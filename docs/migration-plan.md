# WordPress / Movable Type → Astro 移行計画

> 2026-09-05追記: メディアのURL変更は了承済み。旧メディアURLへの転送は必須とせず、元URLと新保存先の対応を保持します。画像回収を待たずに公開本文の暫定取り込みとAstro確認用サイトを実装しました。実施結果は [第2段階の結果](phase2-results.md)、操作は [作業手順](migration-workflow.md)。以下は本番移行までの全体計画で、未完了の項目を含みます。

## 目的と原則

過去の文章を改稿せず、Blogを今後も書ける形で保存する。公開済み投稿・固定ページ・分類・メディア・現行と過去のURL・内部リンク・Movable Type由来情報を対象とする。Markdownで表現しきれない構造を捨てて「全件Markdown化した」とは扱わない。

Git管理する公開用データ、原本の保全、公開サーバーへの配置を分ける。現状調査は完了した範囲を台帳化した段階であり、全データ回収や移行完了ではない。

## 保存対象

| 対象 | 原本として保存するもの | 移行時の扱い |
| --- | --- | --- |
| 投稿・固定ページ | WXR、DB、raw本文、rendered HTML、ID、状態、作成/更新時刻、抜粋、親子/順序 | 公開可と確認したものをMarkdown＋必要なHTMLへ。非公開は配信しない |
| カテゴリ・タグ | ID、名前、slug、説明、カテゴリの親、記事との多対多関係 | 空カテゴリも保存。旧アーカイブURLを維持する方針 |
| 画像・添付 | uploads全体、原寸・派生画像、旧MTディレクトリ、名前、MIME、寸法、alt、caption | SHA-256と出典URLを記録。参照ファイルをローカル配信できるまで照合 |
| URL | WP permalink、旧MT URL、短縮/?p=、添付URL、分類/年/月/ページ送り、feed | 原則同一URL。変更時は対応表から実HTTP 301をサーバーで設定 |
| 内部リンク | href、相対URL、fragment、src/srcset、本文/添付/分類間の参照 | 旧ホストを含む所有確認済みURLだけ対応表で変換。変換履歴を保持 |
| MTの痕跡 | MT entry ID、basename、旧URL、文字コード、テンプレート由来HTML、more、コメント/トラックバック | WP IDと別項目で保存。不明はnull、推測値を確定扱いしない |
| 補助情報 | コメント、トラックバック、RSS、SEOメタ、メニュー、テーマ/プラグイン設定 | 原本を保存。動的機能の再現・公開範囲は別に決める |

## フェーズ1: 原本と環境の確保

1. 所有者からWXR「すべてのコンテンツ」、DBバックアップ、uploads、旧MT/旧ホストのファイルと設定を受領する。[受領チェックリスト](source-data-checklist.md)を使う。
2. 原本はアクセス制限されたGit外の保管先に置き、日時・出所・サイズ・ハッシュを記録して別媒体にも複製する。復元できることを検証する。
3. WordPressのタイムゾーン、パーマリンク、リダイレクト、公開状態別件数、カスタム投稿、プラグイン依存を確認する。
4. WordPressおよび旧ホストの読み取りだけで全体像を確定する。記事削除、テーマ切替、プラグイン無効化、DNS変更はこの段階では不要。

WXRはメディア実体を含む完全なファイルバックアップではない。公開REST APIの `content.rendered` だけではraw本文や非公開データも回収できない。[WordPress公式Export説明](https://wordpress.org/documentation/article/tools-export-screen/)

## フェーズ2: 全件台帳と対応関係

- API・WXR・DB・全子サイトマップ・旧HTML・既存転送設定・利用可能なアクセスログのURLを突合する。複数ソースの同一記事はWP IDと内容で照合し、差分を記録する。
- 現行419投稿・3ページを基準に、受領時点で増減した理由を記録する。年別・状態別・種類別件数も照合し、MT→WP時代の欠落があれば別件として回収する。
- メディア登録、本文、テーマ、CSS、添付リンク、旧ファイル一覧の和集合を作る。HTTP URL、srcset、相対パス、日本語・空白・大文字小文字・重複ファイル名を扱う。
- `hrk-up.net`、`balog.jp`、`note.alchembright.com` 等は所有権と利用可能なバックアップを確認する。外部画像を無条件でダウンロードして自分の資産としない。
- `url-map.csv` と `media-map.csv` を埋める。全件に維持/転送/要確認等の状態と根拠を付ける。未解決項目を黙って除外しない。

## フェーズ3: 少数サンプルの変換

2003年の最古記事、旧画像付き記事、コード/引用/表を含む記事、日本語slug、moreとアンカー、複数カテゴリ、旧MTリンク、2025年の画像記事、home/about/KIROKUNの固定ページを選ぶ。

原本文のコピーから変換し、元データは上書きしない。UTF-8に変換する場合も元のバイト列と文字コードを記録する。本文・追記・改行・コード・リンク・画像・脚注/アンカーを旧表示と比較する。HTMLやショートコードがある場合は、意味を確認してHTML保持か専用変換を選び、変換不能項目をレポートする。古い本文を自動でMDXとして実行しない。

同じ入力から同じ出力を再生成できる変換にする。ID・出典・ハッシュ・変換ツール版・変換警告を記録し、生成先は空のステージング領域とする。手編集済み記事を再変換で上書きしない。

## フェーズ4: Astro基盤と全件生成

- Astroの静的出力とビルド時Content Collectionsを採用する予定。導入時に対応するNode/Astro版を選び、ロックファイルを固定する。第2段階でAstro 7.3.1を導入済み。
- `src/content/blog/<年>/wp-<ID>.md`、`src/content/pages/wp-<ID>.md` を基本とし、分類は `src/data/` で独立管理する。
- 公開ルートは `canonical_path` とURL台帳から明示生成する。ファイル名・記事年・タイトル変更が既存URLを変えないようにする。homeと汎用ルートの衝突を検出する。
- 既存 `/blog/.../` と `/category/.../`、タグ、年/月別、ページ送り、RSSの必要なルートを照合する。機能を維持できないURLも対応方針を決める。
- 画像は `public/media/imported/` に新URLで保存し、旧ホスト・WordPress画像とも対応表で結びつける。メディア旧URL維持は必須にしない。
- 原本保全用HTMLと公開用HTMLは分け、公開側の古い実行スクリプト・埋め込みは動作と安全性を確認する。下書き・非公開・保護記事の除外を明示的に検証する。

[Astro Content Collections](https://docs.astro.build/en/guides/content-collections/) / [Astro deployment](https://docs.astro.build/en/guides/deploy/)

## URLとサーバーの条件

Webサーバーは利用者が用意する。Apache/Nginx等の種別、TLS、ドキュメントルート、アップロード方法、旧ホストの管理可否を確認してから設定を作る。

- 現行の正常URLを200で同じ内容へ。必要な301は同じ記事へ1回で転送し、全件トップへ転送しない。
- `/?p=123`、`?page_id=...`、旧CGIのqueryは静的ファイルだけで区別できない。サーバー側で照合する。実例の取得後にルールを書く。
- `.html`、末尾スラッシュ、エンコード、HTTP/HTTPS、www差、fragmentを検証する。fragmentはHTTP要求に送られないため、新HTMLに元のid/nameまたは互換アンカーを残す。
- 別ドメインの301はそのホストの配信制御が必要。制御できなければサイト内参照の修正と原URL記録までが可能で、外部リンクからの到達を保証しない。
- Astroの静的転送ページだけで実HTTP 301を満たしたと判断しない。実サーバーでステータスを確認する。

## フェーズ5: ステージングと受入条件

公開切替前に、以下を満たした検証結果を保存する。

- [ ] 原本バックアップが復元でき、原本ハッシュとファイル件数が一致する。
- [ ] 移行時スナップショットの全対象IDが、公開または非公開保全など明示した処理結果に一対一で対応する。現状基準は419投稿＋3固定ページ。
- [ ] 本文・日時・分類・旧ID/URLが保存され、サンプルの旧新表示が一致する。変換警告の未処理がない。
- [ ] 対象資産は原本とハッシュ一致、または変換元/派生物の対応が記録されている。移行により生じた画像欠損は0。既存の回収不能資産は個別に確認する。
- [ ] URL台帳の全行を実サーバーで確認し、200または意図した301で正しい内容へ到達する。ループ・競合・新たな404がない。
- [ ] 全生成ページの内部リンク・画像・fragmentが解決する。外部の既存リンク切れは内部の移行不具合と分けて記録する。
- [ ] 分類・ページ送り・RSS・サイトマップが整合し、プライバシーポリシーも旧URLで読める。
- [ ] 非公開原本・DB・WXR・認証情報がGit履歴にも配信物にも混入していない。
- [ ] 別の環境でも固定した依存関係で再ビルドできる。WordPressや旧画像ホストを止めても新サイトの保存対象が表示できる。

## フェーズ6: 切替と復旧

1. まずGitHub Actionsはビルドと検証だけ実装し、ステージングへ配置する。サーバー情報がない状態で本番向け同期や削除オプションを作らない。
2. 切替前に更新を一時停止する時刻を合意し、最終WXR/DB/ファイル差分を取得、再変換・再検証する。
3. 本番リリース用ディレクトリを作成し、旧公開領域を上書きせず、切替可能な形で配置する。リリースIDと転送設定を保存する。
4. 受入結果を確認して本番切替を決定する。DNS変更が必要な場合のみ事前にTTLと復旧方法を準備する。
5. 記事・画像欠損、重要URL異常などがあれば旧ドキュメントルート/前リリース・転送設定・必要なDNS設定へ戻す。旧WordPressとDBは復旧検証・保管期間の合意まで保持する。
6. 切替後にアクセスログの404、旧URL流入、画像応答、RSSを確認し、対応表を補完する。保持期限を決めてから旧環境の廃止を別途行う。

## 次の着手条件

最優先はWXR、uploads以外も含めた旧画像ファイル、旧MTバックアップの確保。サーバー情報が未定でも受領・突合とサンプル変換は進められる。デザイン刷新やプロフィール改稿は保存の検証と分けて扱う。
